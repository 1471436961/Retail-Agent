## 范围与固定 oracle

本批为证据基础设施和回归测试，没有修改 agent/ 生产代码、工具库存、schema、绑定、工作流或生产开关。沿用 M6.1 与 M6.2 的两份固定夹具，不从本次输出生成期望，不修改它们的起点哈希、逐轮读写、当前轮次诊断或完整最终后台补丁。每次执行仍须先独立通过这些固定 oracle；两次相同的错误不能仅凭互相一致通过。

[原生重放 worker](../tests/sdk_m6_replay_checks.py)对全部既有对话各运行两次。第一遍使用新合成后台、新 ClientAPI/Tools/CustomerAgent/SessionClaims；第二遍另建相同起点的后台和全新认领表，并在每个 user 边界、每次工具派发前和每条终止回复后做恢复核查。第二遍每次恢复都重建 agent 与 toolkit，但同一后台的会话认领表继续共用。独立后台的重放不等于在同一实际后台重新发送。

继续执行使用完整 JSON state：JSON 往返后 clone_state 必须与输入全字典相等。另从 canonical history 经 initial_state 重建，核对 history、身份及原来源、提案、任务、所有 operations、handoff、pending read、customer_record 和六类业务 pending；这只核查可派生证据，不声称 history 可复原全部运行时 turn／预算／模型计数。恢复核查期间合成 API 调用列表必须完全不变。

完整轨迹比较含每个 user／工具调用／工具结果后决策／终止回复的消息、完整参数与结果或 state、累计 HTTP 调用的 SHA-256，以及独立固定 oracle 验收的实际结果。SDK message 的顶层 timestamp 由 SDK 自动取墙上时间，两次运行不要求其相等；只去除此字段，保留调用 ID、工具名、全部参数、正文及其他消息字段。报告保存两遍完整场景观察，验证器再次核对固定 oracle 和起点／最终后台哈希；轨迹哈希不冒充签名。

## 重复与中断探针

八个变更 HTTP 动作各有以下三种原生故障场景，预期在 [重放契约](../scripts/local_replay_batch.py)固定，不从输出反推：订单地址、默认地址、支付、取消、商品修改、退货、换货、转接。

| 场景 | 预期和判据 |
|---|---|
| duplicate_receipt | 在执行派发快照恢复后正常发送一次、接纳原结果，再重复交付同一 bundle。业务 journal／身份／来源不变，金额摘要不重复累计，无第二次 API 调用。业务 succeeded、转接 accepted 保留。 |
| lost_execute_result | 工具实际完成一次发送，但整份返回 bundle 丢失；向平台入口交付 error。业务 pending Unknown 保留且没有臆造可见写 journal，转接为 Unknown。晚到原有效 bundle、后续 yes／档案请求、恢复或新工具实例均不能清除它；零调查读取、零再次发送，注入模型不得被调用。 |
| timeout_after_effect | 在合成 request 完成后抛超时。返回并接纳 Unknown journal；业务 pending 已清空，允许真实档案调查读取，但完整原写 journal 不变，明确业务请求不得重发。转接 Unknown 仍终止读取与模型。迟到／重复 bundle 不将未知提升为成功。 |

三类都用旧执行快照调用重建的 toolkit，同时复用实际共享 store。故障注入把合成后台恢复为原起点，排除“状态已改变／地址已经相同”的掩护；这只是测试操作，生产流程没有回滚后台或补偿路径。七个业务动作必须真正得到 write_already_claimed；转接必须得到 handoff_claim_conflict。实际发送次数仍为一，不接受用状态门拒绝代替认领守卫的见证。旧执行快照本身保持不变，拒绝后的工具副本不被拿来替换原已接纳 journal。

重复结果可追加有限拒绝／提示历史，不要求整个平台 state 没有任何变化；要求原 operations、身份及来源、金额证据和发送次数不变。已接纳 Unknown 的调查可能增加 READ operation，不据此声称所有 operations 数量恒定；原 mutating operation 全字典必须保持一致。
