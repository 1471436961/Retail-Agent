## 刷新与业务门

写前核实当前完整提案、真实 user 同意、任务范围/冲突/前置完成及历史未决。刷新客户 → 自有订单 → 相关产品/规格，只有完整校验成功正文进入 history。自有订单引用检查先于订单 GET；新失败读取不能回退旧正文。当前最多 12 READ 工具调用预算不是 HTTP 请求上限。

可信内部刷新读取已经独立验证的同一客户，不用已更改的默认邮编重新搜索。姓名＋邮编来源必须有原 user、lookup/verify 调用和匹配原档案；独立验证入口依旧唯一严格实现。当前姓名及 customer_id 不得切换，缺原始来源或助手摘要不能开放此例外。

刷新同值保持同意，相关状态、地址、payments、余额、价格/可用性/属性变化使旧提案失效。modify_items/exchange 重算公开顺序 float 差价并重跑结算方式规则；实际端口还以可信 requested_options 检查客户请求和所有保留属性。payment_method 核对唯一原 payment 的整单金额、不同已存方式和礼品卡足额；多笔不猜净额。cancel 的已有 refund 风险记录写前受控核实，正常 payment-only 可用。

return 完整提案绑定原成交价预计额、次数和合法去向；预计额为项目十进制合计及 half-up 分精度，不传入 API 或证明结算。开启边界的档案来源被固定，不能用晚取档案补此前礼品卡资格。完整 M5 自然语言流程仍未接入。

## 履约与回执

pending 履约 ID 不在订单/次数超量 → fulfillment_items_conflict；非空履约商品 → fulfillment_requires_review。未知字段 → undocumented_fulfillment_fact。仅 tracking_id 不发明发货/日期/ETA，缺字段不等于已证明未发货。规则在执行和 journal 恢复都调用；按异常记录审查，不等待精确事件定义才实现正常范围。

sent 只表示进入发送边界，不能证明 HTTP 已发生。确定拒绝为 failed；超时/5xx/不可用成功正文为 unknown。合法回执为 acknowledged，随后自有强读回及完整实际效果相符才 succeeded。回执和读回核对完整列表及交易次数，不合并同方式 refund 或净额化；未知或仅后台状态相同不能冒充本次完成。不证明渠道退款到账。

checkpoint 故障保留 persistence_unresolved，不能凭布尔清除；即使效果读取匹配也不释放依赖或发送后继。reconcile 仅重查，不重发，并以 write_rejected / write_sent_unresolved / write_result_unknown 分开确定失败和未决。

## 单次发送的实际保证

call_id 仅 journal 定位，claim_identity 绑定 version＋target；端口按可信 Client API conversation_id 隔离，拒绝用户 state 的授权/会话自报。认领返回必须严格 True，False/None/整数/对象阻断。shared SessionClaims 在锁内认领，dispatch 先于唯一 HTTP；陈旧快照加历史、新端口实例共享表、Unknown 换版本均不能重复发送。

受支持范围为串行会话、完整合法 state/journal 恢复和同后台共享进程表。新后端工具重放使用新表并保持确定请求参数，这与同后台 Unknown 重试不同。新空表配合丢失发送事件的旧 state 无法证明后台未操作；任意进程崩溃、回滚/状态丢失的分布式去重未承诺。不存在课堂新增 CAS/阅读/签名的全阶段前置，也不将内存表称为持久化服务。

宿主角色消息与完整原文是信任边界；项目验证内部一致性并在 SDK submit_operation 返回消息和对应 journal。不能证明用户实际阅读或识别整体伪造宿主历史。跨端点刷新不是原子快照，不承诺消除外部并发。
