## 路径与依据

[returns_intake.py](../agent/support_agent/domain/returns_intake.py) 从真实 user 有限中英文或完整 JSON 解析订单、原商品次数及去向；[returns_session.py](../agent/support_agent/returns_session.py) 有默认调用者：read_session → route_returns → 原 WorkflowBoundary → [returns_tools.py](../agent/support_agent/adapters/returns_tools.py) → ReturnsRuntime/SessionWriteRuntime → 原提案/任务/write journal。不另建身份、确认或账务系统。工具只有 session_json；共享可信 SessionClaims，接受转接后直接工具调用也被原 store 门阻断。

[workflow_registry.py](../agent/support_agent/workflow_registry.py) 统一维护有序 WORKFLOW_KINDS（address/payment/cancellation/items/returns）。通用批次互斥、恢复/slot 校验、模型投影、候选门、转接摘要及生产器 peer 守卫共用它；WORKFLOW_TOOL_NAMES 从这些 kind 派生，并另加 handoff_workflow。当前是五个通用业务 kind、六个内部 WRITE 工具；handoff 保持独立会话生命周期。新增 kind 仍须显式提供边界规则、生产器、schema 门与 SDK 注册，单独加常量不等于开启业务。专项逐 kind 验证实际 dispatch 的历史恢复及全 peer 互斥，未知 kind 和 handoff 不可作为通用业务边界。

## 有限输入与完整提案

合成例：`Return order #TEST1; items: item_blue,item_blue; refund to original`，或 `退货订单 #TEST1；商品: 全部；退款至 原路`。完整 JSON：`Return #TEST1 items: {"item_ids":["item_blue"],"refund_payment_method_id":"gift_a"}`。只允许一个明确自有订单。自然完整 items 子句替换列表；add item 显式追加一次，remove item 只移除唯一无歧义行，JSON 替换完整列表并清除未指定的去向。每次修订从新完整清单报价/复述，不拆成逐 item 许可；条件式去向、混合操作或无法解析的句子澄清。

重复 item_id 表达原购买次数，不去重或发 quantity/自造 line selector。同 ID 不同原价格/规格实例，当前公开接口不能精确指向，返回 instance_selection_unavailable；不猜所选实例。all/全部明确展开原订单完整 item 列表。

复述包含 delivered、每个原单位的名称/item_id/完整 options/原成交价、精确原价总和、预计值及项目显示方法、唯一退款去向/方式标签/渠道时效、一次申请不追加，以及申请不证明结算或到账。沿用已验收原价 Decimal 精确求和后一次 half-up 到分，顾客预计值固定两位；不是替代 float 差价算法，也不是新后台公式。amount_is_estimate=True，aggregation_contract_verified=False、settlement_verified=False，exact_price_sum 原值保存并与完整 spec 绑定。

原路从 transaction_type=payment 的原 charge 方式派生，不用最后支付行/历史 refund/净额代替。多原方式须明确一个；多个合法去向须客户选，唯一合法且当前存在的去向可以直接完整复述。无 charge 如实 original_charges_required，不说零。其他银行卡/未用于该单的 PayPal/新 instrument 拒绝；礼品卡退款不要求余额覆盖预计额，那是扣款规则。原路 method 已不在当前档案时解释现有 instrument 范围并要求合法已有去向或人工协助。

基础规则在未指定去向时仍返回 refund_destination_choice_required，包括只有一个候选的情形；生产器仅把唯一合法且当前存在的去向提出为完整提案，不默默提交。复述明确展示该去向，仍须之后真实 user 的整份确认才有一次 POST。专项分别断言确认前零 POST/无确认记录，以及确认后一次 POST 和正确去向。畸形已接纳支付档案保留 refund_destination_facts_required，不再经重复解析降为笼统准备失败。

唯一去向测试分别覆盖原路银行卡和开启前已接纳的礼品卡；礼品卡场景保留原银行卡 charge，但该卡不在当前档案，只有起点合格且当前存在的 gift 可提出提案。两种场景都检查复述标签、确认前零 POST/无确认以及之后一次 POST 的精确去向；不以银行卡用例替代礼品卡的起点资格证据。M3.1 历史表格已链接到本批，保留当时范围并明确 U7 来源冻结现已实现。

returns_basis 存实际 opening/list/destination user 索引与原文、完整 spec、原价预计额、冻结档案索引/方式和时效；clone/restore 从该 entry 之前的历史前缀重算并严格比较，不信元数据自报，也不追加伪 user JSON。

opening_payment_methods/opening_profile_index 保存在来源记录及相关事实中，并进入确认指纹；它们不是新增 spec 参数，也不上线。spec 仍为 action/target/parameters/amount 四项，退货 parameters 只有 item_ids/refund_payment_method_id。

## 开启来源与提交

开启资格取首个实际 user 退货请求以前最近一次接纳的验证档案；客户先提出请求再验证身份时，首个成功验证档案是本项目可操作流程起点。后续刷新、目的地修正或重新复述不能把晚加 gift 回填到起点。来源链只用历史索引，无本机时间/自报 eligible；验证前不读取私有订单。原内部结构化退货入口与默认生产器并存，默认执行只接管自身来源记录的提案。

首次 prepare 零 POST；后一次邻接真实 user 的完整确认才执行同版本完整 spec，局部/条件/追加/撤回不授权。执行前刷新当前档案及自有订单；状态/原价格/列表/方法变化使旧提案失效或阻断，需新复述和新确认。选择一个候选去向也不是写许可。

check_confirmation 只捕获 TypeError/ValueError/KeyError 并返回 facts_unavailable。退货预计额或去向复核不匹配可能在指纹比较前落入此 code；其他相关事实变化仍可返回 facts_changed。当前生产器对两者都要求重新准备，不能据此声称 facts_changed 全局不可达，也不扩大异常捕获范围。

仅一次 `POST /v1/orders/{order_id}/returns`，body 恰为 item_ids/refund_payment_method_id；不发送预计值/原价总和/来源/quantity，不创建独立 refund。严格申请回执＋之后自有强读回的 return_request 和次数/去向核对才 write_verified。公开后端可能排序 item_ids，Counter 保留重复次数，不折叠。这个结果只证明申请已核实；没有钱款执行、到账、后台特殊精度或处理器事务的证明。

排序专项使用非字典序且含重复单位的 item_red,item_blue,item_red：线上请求保留原顺序，回执及强读回排序为 item_blue,item_red,item_red 后仍核实成功。反例分别在回执或强读回少一份/多一份，结果必须保持 unknown/acknowledged，不能 write_verified；原同 ID 两单位用例继续单独验证次数及原价求和。

409/422 是确定 failed；超时/不可用 2xx 正文是 Unknown；已接回执但强读回不匹配是 acknowledged，均不得假装 verified。结果丢失可能已发，保留 Unknown reservation；新版本/yes/重验/其他业务或转人工不能清除。prepare 只读结果丢失可放弃重试，晚到正文不污染新批次。恢复只重建来源与 journal，不自动重发。

共享 store 中 conversation_id＋version/target 单次认领及陈旧 journal 检查沿用 M3.5；保证范围是同一 live 后端的可信共享进程内表。去重专项故障注入恢复后端旧 delivered 状态，排除状态门的掩护，重建 toolkit 复用真实 store 时必须得到 write_already_claimed 且仅一次 POST。新空表＋丢失 sent 的旧 state 无法证明从未提交，不声称跨进程持久化去重。真实宿主角色/返回 state 是当前提交边界，不把内部工具 shape 当签名/送达证明；模型 candidate、bind 和网关仍排除所有六个内部 WRITE。

## 预算与迁移

共用 256 KiB 参数和 1 MiB 结果预算；每 user 请求最多 12 READ，prepare 预留两读（当前档案/自有订单），无目录读取。完整说明 note 内部上限 4,096 字符；超限返回 returns_recap_budget_exceeded，保留完整原证据、不产生新提案、不截断/拆分，也不发送。这是有限入口限制，重复同一大清单不能解决，须人工协助；最终整段工具文本另受 UTF-8 传输预算约束。发送后结果超限仍是未决交付，不能变成确定失败或零写。

复述预算同时覆盖超长商品名及 40 个正常原单位的完整请求；后者断言后台订单不变、没有部分提案或写 journal，后续 yes 也不能提交。参数预算检查直接比较 API 调用和可信认领表，验证超限在读取/认领/发送之前阻断，不以 JSON 副本的调用方 dict 不变代替此证据。

schema 11 新增 returns_pending 和 returns_dispatch/result/unknown/abandoned/assessment/basis；v1–v10 不得夹带新证据或 pending。真实 [schema 10 fixture](../tests/fixtures/m5_schema10_state.json) 由干净已推送 a0308d7 的原函数在源码改动前生成，保留 M5.2 已接纳清单提案；不是把 v11 改版本号。当前恢复按时间前缀重建完整来源，未来用户/档案不能修复过去许可；五类业务批次仍互斥，转接保留未知业务状态。

clone_state 等价断言检验经过来源/台账重建校验后的合法状态稳定性，单独不证明外部历史真实或零网络。fixture 的 source_commit 字面量比较仅钉住来源元数据，不是生成来源证明。单元模型门测试验证共享常量中的名字被拒绝；真实 SDK 库存测试另将 get_tools() 与 READ_TOOL_FIELDS/WORKFLOW_TOOL_NAMES 对照，两者共同覆盖工具注册及模型门。
