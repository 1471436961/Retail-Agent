## 有限请求与完整提案

合成例：`Exchange order #TEST1 items; item item_blue: color to red; pay with card_a`，或 `换货订单 #TEST1 商品；商品 item_blue: color to red；结算方式: card_a`。完整 JSON：`Exchange #TEST1 items: {"replacements":[{"item_id":"item_blue","options":{"color":"red"}}],"payment_method_id":"card_a"}`；精确变体可用 replacement_item_id，或 `variant item_red`。条件语法与 M5.2 共用，属性值须匹配真实目录，不自动翻译/猜值；不支持的自然语言澄清。

一个明确自有订单，完整原单位→新规格清单，一个客户选择的已有方式。自然同单行修正/合并、显式 add 保留出现次数、remove 仅移除唯一无歧义行；完整 JSON 替换整个 draft 并清除遗漏方式。每次清单/方式/条件修正重算和重新完整复述，不拆成逐项许可。quantity、跨产品、未知原 item、超出原购买次数、同 ID 不同价/属性实例、混合业务或多订单请求均有具体拒绝/澄清；不猜选中实例。

商品修改与换货不支持将 all items/全部商品自动展开为替换清单：每个原商品仍须明确目标规格。该意图返回 bulk_replacement_targets_required，提示逐原商品列出目标，零额外读取/业务发送、不生成提案；不会只执行同一消息中已列出的部分。退货 all 仅展开原购买单位、不需要新规格，故与替换流程语义不同。

真实 user 索引与原文、规范 criteria/显式回退及选用分支、完整原名称/选项/成交价、新 item/完整新 options/当前价、spec 保存于 exchange_basis。clone/restore 对该记录之前的历史前缀重新计算并严格比较，不信 basis 自报、不添加伪 user JSON，也不让未来证据修复过去请求。复述显示全部采纳条件和选用分支，保留属性、软偏好、回退、并列和未知语义与 M5.1 一致；并列或未知不任意选择或触发回退。

差价严格使用订单原成交价→目标当前目录价，按完整请求顺序 float 累加，最后 round(total,2) 一次。正差价显示补款，负差价显示退差价，零差价明确显示零；不是退货预计额 half-up。一个已有银行卡、PayPal 或礼品卡；正差价礼品卡覆盖全部差价，不拆付、不自动回退。负差价允许其他已有方式，不套用退货 RT-02 的原路/开启礼品卡限制；零差价也不能省略方式。

复述包含 delivered、订单号、每个原/新 ID、原名称/完整原选项/成交价、完整目标选项/当前价、有符号差价与客户方式、一次申请及提交后不追加/改方式，最后一个集合级确认问题。首次准备零 POST，之后邻接真实 user 的完整确认才可提交同版本整份操作；条件、局部、撤回、改口或非邻接 yes 不授权。

换货仅记录申请，不在循环内替换订单原商品，原单位间互换可表达；共享 resolve_replacements 只在 pending 商品修改启用逐步匹配限制。两种动作都保留原次数、同产品、库存、选项和价格校验，未取消 U5。

## 提交、回执与不确定结果

执行前重读当前档案、自有订单和完整相关产品目录并重跑原来源条件/筛选/报价。价格、方式/礼品卡余额、状态、库存或新竞争候选变化阻断旧选择，需重新完整复述和确认；即使旧 target 本身没变，也不能忽略新并列候选。

仅一次 POST `/v1/orders/{order_id}/exchanges`，body 恰好完整 replacements/payment_method_id。不发差价/条件/来源/quantity，不拆清单，也不创建独立扣款或退款端点。200 封闭 OrderExchange＋之后自有强读回核对 exchange requested、完整替换对、次数、方式和有符号差价，才 write_verified。这个结果只证明申请已核实，不证明实际结算、退款到账、新件出库或发货。提交后不追加、不修改已选方式，不再次换货或同单退货。

回执允许整个替换对重排，Counter 比较 `(existing_item_id,replacement_item_id)` 保留每对的对应关系和次数；强读回还须与回执完整一致。不得分别排序旧、新 ID 后重新配对。固定上游的独立排序可产生错误配对：合成探针对此返回 Unknown，不能 verified，不伪造正确清单、不自动重试或补偿。这是已知适配边界，有证据与确定处置，不等待平台另给算法。

409/422 为 failed；超时/不可用成功正文为 Unknown；有效回执但强读回不符为 acknowledged。丢失执行结果保留 Unknown reservation，不声称零写或成功，不因 yes/新版本/转人工清除。只读 prepare 丢失可放弃重试，晚到结果不进入新批次。共享 live 后端 SessionClaims 以 conversation_id＋version/target 认领；专项恢复后台旧 delivered 且删除换货记录，排除状态门后重建 toolkit 复用 store 仍只一次 POST。新空表＋丢失 journal 的陈旧状态不提供跨进程/崩溃持久化去重保证。
