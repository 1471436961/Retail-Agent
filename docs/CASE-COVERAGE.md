## 3. 建议本地测试批次

这些是离线测试组织方式，不是远程 --cases 参数，也不修改网站保存范围。各批次可以复用同一公开案例抽象出的不同要求。

| 批次 | 对话/规则组合 | 核心断言 |
|---|---|---|
| B0 接入回归 | 保留现有邮箱搜索→档案读取流程；补齐协议替身验证 | 先验证后读取；已推送历史 t1 接入通过，当前变更的远程验证仍按推送授权执行，不外推业务覆盖 |
| B1 身份与只读 | 已验证/未验证 × 自有/非自有订单 × 详情/查询 | 无越权详情、无写调用；安全查询不陷入重复确认 |
| B2 状态边界 | 7 个状态 × 地址/支付/取消/商品修改/退货/换货 | 允许表精确；用户描述不能覆盖实际状态 |
| B3 确认控制 | 未确认、早期同意、有效同意、局部同意、追加、撤回、预算或支付变化 | 执行内容等于最新有效提案；禁止场景写调用为 0 |

## 4. 逐条追踪格式与当前产物

M0 已在 [CASE-REQUIREMENTS](CASE-REQUIREMENTS.md) 为每项案例拆出原子要求，引用 N/E/B 原文行号，以规则/API 组合关联行为、条件、允许/禁止轨迹和实施阶段。每行 `Axxx-yy` 对应未来 `AT-Axxx-yy` 场景；目前统一标记测试待实现，不创建不存在的测试函数。后续按下列字段补实测证据：

| 字段 | 示例/要求 |
|---|---|
| `case_id` / `requirement_id` | 案例 ID 加本地原子要求序号；只存在开发文档/测试中 |
| 原文位置 | 需求、期望结果或业务要求的行号；不只记录结果标签 |
| 行为 | 如“确认时客户缩小换货清单后，仅执行新的清单” |
| 规则 | 对应 POLICY-REGISTER 编号；无来源则标待裁决 |
| 数据/API | 查档案、订单、产品/item，再按合法动作调用端点 |
| 对话条件 | 何时提出，客户如何改口，旧确认为何失效 |
| 预期轨迹 | 允许的读/写顺序；禁止调用；副作用次数 |
| 预期结果 | 正确记录变更和事实回复；精确金额来自测试 fixture/API |
| 本地证据 | 测试文件和函数、最近结果；未写测试时标待实现 |
| 远程证据 | 未运行，或真实 job/case/结果；不要填本地模拟分数 |

公开材料给出的具体商品、金额和地址可作为测试 fixture 与预期断言；不得把这些固定值、案例编号和评测范围带入正式 Agent 的决策逻辑。合成测试应变换 ID、商品属性和金额，检验规则而非记忆答案。
