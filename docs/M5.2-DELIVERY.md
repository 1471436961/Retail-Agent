## 实现和可达路径

[items_intake.py](../agent/support_agent/domain/items_intake.py) 只解析真实 user 的有限请求、完整商品列表、条件和结算方式；[items_session.py](../agent/support_agent/items_session.py) 从已接纳档案/订单/完整目录构建清单、调用 M5.1 纯筛选、展示完整提案、等待后一次确认并执行。默认 read_session → route_items → 内部 [items_tools.py](../agent/support_agent/adapters/items_tools.py) → 原 WorkflowBoundary/SessionWriteRuntime/写 journal；这些函数有默认生产调用者，不是未接线内部原型。工具仅接 session_json，不接受任意 HTTP、quantity、confirmed、条件成立布尔或模型自造规格。

有限示例：`Change order #TEST1 items; item item_blue: color red; price <= original; cheapest otherwise color green; pay with card_a`。中文示例：`修改订单 #TEST1 商品; 商品 item_blue: 颜色 red; 结算方式: card_a`。订单/商品 ID 必须来自自己的真实记录，选项值按实际目录精确匹配；示例是合成数据。

支持已知属性等值、明确预算、原价上限、用户显式偏好 tiers、一个 otherwise/否则回退、最高属性/最低价格目标及任意/relax 指定属性。未知测量、并列或未支持条件要求澄清；主分支未知不会触发回退，不用目录序/item_id 猜选。自然语言不是任意语言模型解析；结构化完整列表也支持每行 options、六字段 criteria 或明确 replacement_item_id，封闭字段拒绝 quantity 和客户端授权标志。

自然语言 `item <id>: <该行完整条件>` 更新该行，须给出这次采用的完整行条件；`add item <id>: ...` 显式追加一次，重复次数不折叠。同一订单后续自然语言列表与已有 draft 合并，并不重置整单清单；重置须使用完整 JSON 替换整个 draft，或用 `remove item <id>` 明确移除唯一行，重复行歧义不猜实例。自然属性修订不是任意句子的增量理解；每次更新后的全部有效条件都随新复述展示。方法必须由客户指定，条件式或冲突的多个方式先澄清，支付回复不能悄悄修复一个畸形/被禁止的商品列表。

## 清单、条件来源和确认

items_basis 保存实际 user 索引、相关原文、规范 criteria/选用回退分支、目标规格、原/新价格和完整 spec；按该记录历史前缀重新计算，篡改条件/来源/清单会被 clone/restore 拒绝。用户不必自己编写六字段筛选 envelope；可信 producer 派生 criteria，没有向 history 追加伪 user JSON。采纳条件逐项展示，选择唯一候选/回退分支不是确认或写许可。

清单一次性完整复述包括所有原/新 item、完整新规格、原成交价/目标当前价、按请求顺序 float 累加并最终 round(total,2) 的总差价、单一已有结算方式和单次锁单限制。正差价礼品卡必须覆盖全部金额，不拼卡或部分扣款；负/零差价也明确选择一个已有方式。没有另加显示合计算法，不用原规格当前目录价代替原成交价。

复述最后明确询问 `Anything else you would like to change before I submit?` 并等待之后真实 user 的整份确认。统一集合渲染使用 `presentation_mode=items_last_call`，将确认说明与完整提案放在补充询问之前，不再附加逐项或集合确认问题；正常复述仅一个生成的问题。该模式与展示文本一同恢复校验，不能只修改返回文本；没有模式的旧展示仍按旧渲染恢复。S08/S10 CF-03 允许同一消息含完整复述和最后补充询问，不要求两个重复 yes。追加/删减/修正、条件/价格/库存或唯一性改变重新展示完整提案；局部、条件、撤回、尚在考虑及“yes, but add…”均零提交。有限完整确认沿用 M3 识别器（如 yes/确认/就这些，确认修改），不声称覆盖全部自然语言。

客户复述逐行展示采纳的主条件、回退、保留/放宽属性、偏好层级、排序优先级、实际选用分支和完整新规格/原新价；来源索引与原文仍完整保存在 items_basis，不在客户文本重复内部 JSON 元数据。八条重复原商品实例的合成列表已验证完整展示、确认及一次提交，不把此例理解为任意长度保证。

## 写前、结果和一次性限制

执行先复核原完整确认、身份/归属、精确 pending、履约和任务依赖，再刷新档案、自有订单及完整相关 product 目录并重跑选项筛选。即使旧目标没变，新竞争候选也阻断旧唯一选择；候选/报价变化重新准备，不复用旧同意。其他未完成业务任务不被静默覆盖；混合取消/商品请求保留原取消冲突诊断。

仅一个 `POST /v1/orders/{id}/item-modifications`，body 只有完整 replacements 和 payment_method_id；不发送报价、条件、来源、quantity 或自造 occurrence selector，不拆成逐条提交。原共享回执/自有强读回核实完整商品效果、支付记录和 literal `pending (items modified)`；成功锁单后禁止第二轮商品/地址/支付/取消，不开放短时追加窗口。不把交易记录等同实际退款到账。

409/422 是明确拒绝；写后超时、不可用成功正文、错读回或丢失执行结果保留未核实/Unknown，不自动重发。prepare 无业务副作用，其结果丢失可以安全放弃重试；execute 的 Unknown 不能用新请求/版本/yes 清除，阻断其他业务及模型。参数 256 KiB、结果 1 MiB、每 user 请求 12 READ 和复述说明 4,096 字符是内部预算；4,096 约束条件/规格说明 note，并非完整消息的总字符限，完整返回另受字节预算约束。说明超限返回 `items_recap_budget_exceeded`，不生成新 basis/提案、不裁剪、不拆清单、不发 POST；相同超长输入重试仍被拒绝，明确说明此入口无法提交该清单、需要人工协助。它是本库容量边界，不是业务政策规定商品数量上限。结果超限若发生在发送后，保留 Unknown reservation，不将丢失回执当确定拒绝。默认串行共享 SessionClaims 防重复范围沿用基础阶段；换新空表且丢失 sent、任意跨 worker/崩溃持久化、整个宿主历史真实性/送达仍不在保证内。

零差价不再跳过新增支付行核验：只接受保留完整原交易前缀且没有新增行，或一条所选结算方式的零金额 refund。固定上游 `retail/tools.py` 的商品修改函数无条件追加交易，差价为零走 refund 分支（约 525 行）；本库因此不凭空要求后端必然零新增行。额外非零行、错方式、payment 类型或重复零退款均不得 verified；这不是课堂后端实测或退款到账证明。
