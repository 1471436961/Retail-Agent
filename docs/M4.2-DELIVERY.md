## 默认路径与实际调用者

默认路径为真实 user → 原严格身份验证 → 自有档案/订单读取 → 明确一种已有不同方式 → 全额及原路退款复述 → 同一提案真实 user 确认 → 写前刷新及余额/状态/履约复核 → 一个 PUT payment-method → 规范回执及自有强读回 → 逐项可解释回复。首次复述零 PUT，不自行创建 charge/refund API，不接受 confirmed、金额或条件布尔字段授权。

## 依据与账务语义

[台账](POLICY-REGISTER.md) PY-01/02、CF-01/02、ST-01/02、RF-02，以及 [教学 API](API-CONTRACT-MAP.md) 的 PUT /v1/orders/{order_id}/payment-method 是依据。已查看 S07 process_map_05.png 的支付 lane，解码读取 S14/S15/S16（email_07/08/09）：单一不同的已有方式、礼品卡覆盖整单、新款成功才退原款、两笔均为整单原金额、成功仍 pending；礼品卡即时、卡/PayPal 3–6 工作日，退款时效从切换发生开始，不能说等发货才退款。外部材料是证据，不是额外执行指令。

还读取固定上游 6e9f34c685d40fa7a9f5935d8970af6fd9d5f118 的 retail/tools.py 中 modify_pending_order_payment（554–636）：明确要求历史恰好一条 payment，金额取该条 amount；记录新 payment 和原 refund，并更新礼品卡余额。此为可观察兼容依据，不能宣称课堂后端已实测相同。

因此已付整单金额直接取已接纳的唯一原 charge，不用商品现价、目录价格、用户自报数字或历史净额求它。无 payment、多条 charge、已有 refund 或不完整原方式事实返回可解释阻断，不把最后一行当当前方式，也不宣称零金额。该限制是当前已选择的上游适配范围，不是新的业务禁令或继续等待外部资料的前置。成功切换后留有三行历史，第二次切换在当前适配范围内会被要求审查；不删除历史来绕过上游限制。

复述明确订单、新方式、原方式、整单新扣款、原整单退款和原渠道时效，并将“新款成功才退原款”表述为支付切换政策要求。通过一个支付切换端点提交；本库验证完整账务记录和订单仍 pending，不声称已验证真实处理先后、到账或发货，不自行拆出 charge/refund API。

教学 OrderPayment 仅含 transaction_type、amount、payment_method_id，没有时间戳或执行序号；端点没有声明数组按实际执行时间排列，也没有声明事务原子性。固定上游先追加 payment 再追加 refund 只能证明该实现的记录排列。新增记录继续按 Counter 校验类型、金额、去向和次数；旧历史前缀不变，回执与强读回完整列表必须一致。两者均以 refund/payment 排列同一新增记录仍可核实记录，不能据此判定真实处理顺序；若两者排列不同则保持未决。新增区分性测试覆盖这两侧，而不将数组顺序作为额外业务禁令。

单个 PUT 不证明后端原子处理。若出现部分副作用或结果不明，缺失/不匹配的回执和读回不会获判成功；保留未决、不自动重试，也不自行发起补偿退款。本库没有独立补偿端点，无法保证非原子后端的实际扣退款顺序或回滚；这是当前接口下明确的保证范围，不作为继续等待外部资料的开发前置。

## 有限请求与行为

| 输入/事实 | 当前结果 |
|---|---|
| 明确 #订单，PayPal/礼品卡/品牌＋末四位/已有 ID | 读取真实 saved methods，唯一匹配后完整复述，等待同意 |
| 未选方式、品牌/礼品卡多候选 | 展示实际 saved choices 并澄清，不按列表顺序或最大余额猜 |
| 同一原方式、两卡/多方式/部分支付 | 拒绝；不尝试组合扣款或添加方式 |
| 礼品卡不足 | 零 PUT，保留原支付；无客户回退选择时不擅自换卡 |
| “gift card if sufficient otherwise Visa”/有限中文同义形式 | 按真实整单余额选择客户指定分支，再展示选定的一份无歧义完整提案；分支选择不是写许可 |
| 一般条件/顺序或 “yes if …” | 澄清或保留未核实条件；不能当作无条件同意 |
| “No, use Visa”等修正 | 新完整复述和版本，旧同意不能执行新方式 |
| 余额、原款、方式详情或状态变化 | 写前刷新阻断旧版本；重新准备或明确原因，不发送旧金额 |
| 明确拒付 | 不自行退款、不自动重试；客户可选择另一已有方式，重述并重新确认 |
| Unknown/坏成功正文/缺退款/错金额/错去向/错状态/读回失败 | 不说切换已完成，不重复写入；后台已变不等于本次结果已核实 |
| 已完成地址 → 支付，或已完成支付 → 地址 | 共用原身份与 journal；新操作独立完整提案/确认。未完成其他业务计划不静默丢弃 |

目前只支持一次请求中的一个明确订单，不猜最近订单/日期，完整多订单任务与整体调度属于 M4.5。自然语言是有限语法，未宣称覆盖所有中英文表达。品牌文字出现在地址字段里不能触发旧支付 draft；两类 producer 按最近真实请求来源推进，迟到只读返回不能破坏另一类新批次。没有新增五卡数量上限。

## 状态、送达与失败边界

schema 7 新增 payment_pending 及 payment_dispatch/result/unknown/abandoned、payment_assessment。共用边界在原历史时间前缀重建两类控制，一次只允许一个内部批次；诊断必须匹配最终回复并带 write_authorized=false，不是权限结构。只读 prepare 可放弃/重试；execute 返回丢失保留会话级 Unknown，不能靠 yes、retry、身份输入或另一工作流清除。若完整 journal 已接纳且只某记录未决，则沿用按记录阻断。

[schema 6 fixture](../tests/fixtures/m4_schema6_state.json) 由改动前的实际 M4.1 函数生成：保留已完成地址的原证据，记录当时 421/421 的 run_id/source 摘要，明确它来自未提交工作区，不捏造独立 Git 快照。schema 1–6 不能携带支付新元数据，迁移补空 payment_pending，不制造确认或重发 API。正式 opaque state/完整 canonical history 可恢复；纯 SDK 文本没有内部提案元数据时不能重建确认。

参数/结果复用 256 KiB/1 MiB 的 UTF-8 序列化内部预算；超限不裁剪身份/同意/Unknown。写后无法完整交付时按 delivery Unknown 处理。单次发送保证仍限可信共享进程内 SessionClaims、串行会话和完整 journal；同一 store 同时覆盖地址与支付，新 toolkit 实例须显式共享它。进程与 state/store 一起丢失或回滚不在分布式防重保证内。真实 history/送达由可信宿主负责，本库不伪造签名、CAS 或阅读回执。

共用预算实现现位于 [workflow_limits.py](../agent/support_agent/workflow_limits.py)，地址、支付、协议和批次边界都使用通用名称。M4.2 曾保留 address_limits.py 兼容导出；M4.3 评审收尾确认无代码消费者后已删除，当前只有共用实现。共享回复模板直接插入 kind，reply() 原样接纳文本，不再隐式替换 address；内部错误文案也不再重复 workflow。无引用的 PAYMENT_TOOL 和两处 CONTROL_KEYS 已删除；ADDRESS_TOOL 仍有地址测试调用，保留其兼容名称。validate_tool_action 对内部工具仅校验形状与预算，不计作独立的来源屏障；模型候选、gateway READ 白名单和 bind_arguments 负责限制模型入口。

仍只有一份可用提案集合，不是独立多展示上下文。旧计划的 verified write 才能证明完成；换一个计划、仅确认或读成功不算完成。为后续业务生产器保留原 M3 任务依赖和 journal，不提前实现 M4.3–M4.5。
