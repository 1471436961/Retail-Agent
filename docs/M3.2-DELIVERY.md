## 本批实现和接入范围

已实现内部结构化提案、完整确认与恢复的离线范围。自然语言业务提案生成、局部确认/追加/条件分支、多订单任务和实际执行仍属 M3.3–M5。默认 Agent 仍只自动路由已有只读业务；模型候选没有 proposal/confirmed 接口，工具目录仍为八个 READ 工具。M3.1 的退款合计边界不变，未知退货合计不能生成可确认的完整报价。

内部 specification 严格包含 action、target、parameters、amount 四项；不接受额外 confirmed 字段。target 明确 customer_id，订单动作还必须有 order_id，默认地址只绑定客户档案，不能顺带修改订单地址。地址绑定全部五个必填字段及 address_line_2（缺省正规化为 null）。商品清单保留顺序、重复次数与完整 ID 对，不接受 quantity/occurrence/行选择器。

金额有明确语义：地址为 not_applicable；支付切换为 order_total，并绑定逐付款退款依据 refund_rows；修改/换货为有符号 price_difference；取消为 per_charge_refunds 的完整原 charge 行。数字不强制转字符串、不再次舍入；取消/支付的退款依据逐行与已接纳订单 payment 记录一致，既有 refund 不混入。refund_rows、amount 和 facts 都是内部确认字段，没有作为新增 REST 字段发送。

提案前重用 M2 时间前缀恢复，要求已有独立身份来源、匹配档案、自有订单引用和已接纳订单读取，状态再由 M3.1 判断。待处理读取、转接状态、外部客户/订单、未解析原商品次数或未保存支付方式不能进入提案。原商品选择复用 resolve_return_items，取消依据复用 cancellation_refund_basis，状态复用 order_state_rule。

修改/换货现须有此前已接纳的 get_product/get_item 目标目录事实；按替换列表次数/顺序绑定 item_id、price、available、options，记录原调用 ID/工具名及可用的产品外层来源。CatalogItem 不被要求具有 product_id。缺目标或快照中不可用时拒绝提案；完整产品重读删除目标时，不保留之前的旧目标记录。已接纳的相关价格/属性变化、不可用或消失阻断旧确认。来源元数据在恢复时精确核对；语义摘要不含来源调用 ID，因此相同事实的重读或无关目录变更不导致多余版本。被拒绝批次和未来读取不能建立此前报价依赖。

这些检查不替代业务报价生产器：order_total 和 price_difference 由未来可信流程完整解析并交给本入口；本入口验证类型、已接纳目标可用快照及绑定内容，不证明整单总价算法、当前支付方式、礼品卡足额、规格同产品/符合请求或差价确实对应这些价格，也不证明后台此刻仍可用。商品偏好/回退、目标规格及差价生成仍待 M5；支付完整资格和后台扣退路径仍待 M4。依赖变化后，生产器必须先重新解析报价，再提出新版本，不能仅重新确认旧报价便宣称它已正确。测试中的新版本断言仅验证失效/版本机制。confirmed 不替代这些规则。

## 版本、消息来源与恢复

每次新复述创建严格递增整数版本。语义摘要覆盖 specification 及已接纳客户/订单/相关目标目录快照；字典键排序，列表顺序和次数保留。有限 int/float 用精确整数比规范化比较，例如 -1 与 -1.0 同额；bool 保持独立类型，大整数不强制转换 float，原存储金额不改变，不新增计算/舍入算法。摘要不含随机性，不是身份凭证，也不能证明被整体伪造的历史是真实外部对话。记录同时绑定此前真实 user 请求索引、完整 assistant 复述索引和其后 user 确认索引。

present_proposal 记录待返回的复述并返回消息/状态，不掌握传输送达回执。可信调用方必须一起提交返回文本与对应状态；丢弃文本却保存提案状态违反这个调用约定，属于整体伪造之外的独立风险。目前没有平台发送失败/原子提交证据，不声称用户已经收到或阅读。M3.5/首个写流程接入前须核实平台提交语义、失败处理，并纳入威胁模型；后台订单刷新不能证明复述送达。当前没有为缺少的平台能力发明消息 ID、阅读回执或完整性保护。

复述由确定性渲染器生成，包含具体动作、目标、完整字段/清单、金额和支付/退款去向，最后只问该完整操作是否获同意。商品修改同时明确清单完整、没有其他修改，并等待之后的用户回复。此处借用 CF-01–03；原始 S03 会议的 00:24:54–00:27:43 明确要求具体操作关联，否决“任意肯定词都算”和魔法词要求，来源见 [规则台账](POLICY-REGISTER.md)。

当前离线识别器只接受直接指向刚展示整份提案的若干清楚中英文同意表达；不是政策规定的封闭词表，也未声称覆盖全部自然语言。“yes, but …”、局部、条件、否定、沉默、偏好和模糊 sure 不确认，保守改为 needs_review；之后的 yes 不能补授权过去版本。插入其他助手问题后，同意不能关联原提案。模型、工具或助手说 yes 都不构成用户确认。更多语义识别及局部范围操作留给 M3.3。

确认字段由 reducer 从已记录原文生成。clone_state 从同一历史重建台账，严格 JSON 比较，拒绝布尔 true 冒充整数版本 1、伪状态、旧版本、错误引用、删除/改角色的用户证据、篡改复述与不一致快照。历史恢复重新检查每个展示位置之前的 M2 证据，未来输入不能授权过去的提案。确认匹配比较绑定的客户、订单与相关目标目录事实；它不主动刷新后台，也不替代 M3.5 写前新读取。未绑定的完整业务事实仍由未来生产器/写前门控核实。

check_confirmation 复用 M3.1 的 decision/code/message/rules/details 结果，details.confirmation_matches 只说明同意匹配。code 区分 invalid_version、invalid_state、invalid_specification、proposal_required、version_mismatch、specification_mismatch、confirmation_required、handoff_blocks_consent、pending_reads、facts_unavailable、identity_mismatch、facts_changed、consent_matches；输入构造错误另带 input_error，损坏状态带 state_error。布尔包装对坏状态及非法参数返回 False。底层 clone/恢复仍严格抛 InvalidState/InvalidProposal；平台入口只捕获这两个明确异常，不泛吞其他错误。

平台对损坏状态/历史返回安全说明及终止型 session_block 包装；quarantined_state 保留完整可 JSON 化的原证据，不修改原输入。不能持久化的非 JSON 证据记录 evidence_retained=false。包装不是另一套可授权身份或正常 schema 状态；后续消息/提案持续阻断，不调用模型/API、不重放 pending，不静默重置或自动恢复。有效状态上的 InvalidProposal 则保留身份与历史，追加参数/事实需核实的说明，等待未来工作流修正。

相同且已确认的语义/快照可以保留原确认证据，不重复索取同一确认；重复肯定不生成第二份证据。助手 ACK 记录 proposal_ack={version,fingerprint,confirmation_index}，恢复先核实已有真实 user 同意，不能由 ACK 创造同意；重复肯定复用的是标记而非固定英文文本。新版本使前版 superseded 并清除其可用确认。台账只有最后一份提案可用，不支持独立多项局部许可；对应功能待 M3.3/M3.4。

schema 1 仅迁移带必需 proposals=[] 且无提案/ACK 元数据的旧状态；缺键、非空旧确认拒绝，未扩展为缺键兼容。固定 [迁移 fixture](../tests/fixtures/m3_schema1_state.json) 使用 9b323d3 原始 state.py 函数恢复合成只读历史生成，测试不依赖运行时 Git。真实 v1 本来具有该键，旧测试并非空转，现已换成更直接的旧形状证据。项目 JSON history 的 assistant.proposal/proposal_ack 元数据可以恢复版本及 ACK；普通平台 AssistantMessage 只有文本而无元数据时不能重建确认，保持无确认并待重新展示。SDK 投影保留复述与真实 user 原文，不发送内部元数据作为模型授权。schema 2 的提案元数据/指纹在提交前随审计修订，首次源码提交为 610f488；修订前的非空试验台账不能补造迁移授权，应保持阻断并核实原历史、重新展示。无提案的合法 schema 1 迁移不受影响。

当前索引依赖完整未裁剪 history。Q2 仍未实施；后续摘要须保护请求、复述、确认、独立身份链及读取批次，与新的 schema、clone、恢复、门控和模型投影一起验收，不能删除来源后绕过校验。见 [证据保留设计](STATE-EVIDENCE-RETENTION.md)。
