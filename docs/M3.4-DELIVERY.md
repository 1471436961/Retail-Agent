## 依赖、冲突与逐记录诊断

| 请求关系 | 计划行为 |
|---|---|
| 同单订单地址/支付方式与商品修改 | 地址和支付各自是商品修改的前置任务；商品先被提及也不能先锁单。地址与支付之间没有凭空规定先后 |
| 同单取消与任何其他订单动作 | 双向冲突，先澄清最终选择；只展示/确认取消一项不会抹去请求计划中仍未解决的另一动作 |

| 不同订单、客户默认地址与订单地址 | 图不建立跨记录的隐式依赖；当前提案集合内，某单锁单、缺事实、改口或读取失败分别判断。确认台账的集合替换边界见下一行 |
| 展示新提案集合 | 当前只有一份可用提案集合；新展示遗漏的旧操作会失效，即使属于另一订单。新集合重新纳入未变化、事实相同且已确认的旧操作，可通过 reuse_version 保留原 user 证据；不支持多个展示集合分别长期持有有效确认 |

| 重新选择计划 | 新计划原子替换当前 tasks，旧计划原文仍留 history；省略任务不记成功，也不作为实际完成的证据。可信生产器仍须先核实客户真实选择 |

`inspect_task_plan` 返回 decision/code/message/rules/details。总结果 task_plan_assessed 表示诊断已完成，不表示所有任务均允许；每项 assessment 单独保留规则/确认拒绝原因、proposal_version、depends_on 和 conflicts。候选集合只包含 preflight_candidate，所有结果明确 write_authorized=false。

跨单展示实测对照：A 已确认后仅展示 [B]，A 返回 proposal_required；新集合为 [A, B] 且只有 B 参数变化时，A 保留原确认索引并仍为 preflight_candidate，B 须新确认。本批不修改 M3.3 的替换语义。未来业务生产器须维护拟保留的完整操作集合；若要实现按订单独立持有多个提案上下文，须连同版本、回复范围、恢复和门控另行设计验收，不能只删掉 supersede 或取消来源校验。

诊断顺序为坏 state → 会话 handoff/pending 批次 → 各任务冲突 → 已接纳身份/归属/订单状态及最后订单读取尝试 → 当前完整提案与确认 → 同单依赖。当前未确认、条件、改口、撤回、已接纳事实变化沿用原确认 code；没有借计划刷新确认或放宽业务规则。

最后一次针对该订单的 get_order 或不带状态筛选的 list_customer_orders 若失败、缺回执、错配或批次拒绝，返回 order_read_unresolved。不会从之前接受的旧正文把这次失败解释为已刷新；后续成功同值重读可解除此读取阻断，仍重算确认匹配。pending 整批未解决时全会话阻断；已经结束的失败读取仅阻断受影响记录。此检查不等于 M3.5 关键事实新鲜度/完整履约控制，也不覆盖所有目录或档案刷新失败。

已确认的商品修改若仍有同单前置任务，返回 dependency_result_required；前置明确拒绝时返回 dependency_blocked，同时不凭空撤回该商品提案的真实同意。该任务自己的拒绝、条件或事实缺失优先保留。前置确认、相同地址已在后台、读 API 成功和从计划中删去任务都不构成成功写回执。

**本批没有业务结果 reducer，也不释放执行依赖。** 候选只可交给 M3.5 前置核实；首个业务流程须接入已发送操作、明确失败/Unknown、写后强一致核实及依赖完成/撤销判定，未知结果不得自动重试或放行后继。本批“独立推进”验收的是按记录产生独立候选和阻断诊断，未验收实际订单提交、后台完成或通用自然语言任务调度。

## 来源、迁移与信任边界

task_plan 仅作为独立 assistant 元数据，绑定最近此前真实 user 的 history 索引；任务 ID 按计划展示索引及组内顺序确定，不使用授权 token、时间窗口或跨会话变量。恢复重新核对此前身份与客户订单引用、计划正文、输入形状和图；tasks 必须与重放结果严格相同。未来 user 不能授权过去的计划，混合计划/展示/ACK 元数据拒绝，外加 status=succeeded 或篡改依赖/目标/索引同样拒绝。

schema 1/2/3 只迁移其原有 tasks=[] 的合法形状，并拒绝携带 task_plan。原 v1/v2 固定 fixture 回归仍通过。新 [schema 3 fixture](../tests/fixtures/m3_schema3_state.json) 在修改前由基线 3460329 原始函数与合成 API 生成，包含 M3.3 局部 user 确认，迁移保留原 history/proposals/身份与部分确认。没有放宽缺 tasks 键、未知任务进度或旧 schema 夹带新元数据。

普通平台 AssistantMessage 文本没有内部 task_plan 时，不重建任务，也不从“已完成”文字重建进度。真实 SDK 投影保留计划展示文本和 user 原文，内部任务图/元数据不送给模型作许可。计划和返回状态须一起提交，但当前没有送达、签名或历史完整性保证，继续受 [M3.5 威胁模型待办](OPEN-ITEMS.md) 约束；记录计划不证明 user 看过，也不证明可信生产器准确理解了全部自然语言。

Q2 须保护 task_plan 原文、用户来源、顺序/计划索引及同时保留的 proposal 来源链，见 [证据保留设计](STATE-EVIDENCE-RETENTION.md)。任务恢复加入重复前缀校验；无性能上限或裁剪验收，不能省略来源检查来提速。
